# 0009. Error contract

Status: Accepted · 2026-11-03

## Context

Scryguard's API is called by the dashboard, by scripts holding API keys and
by operators. Each caller has to decide from an error alone whether to fix
the request, retry it or give up. Errors are also a common leak: library
messages can carry rejected values, SQL fragments, file paths or repository
contents, and Scryguard handles code that its users have not published.

## Decision

Every error response, on every route, has one shape:

```json
{
  "error": {
    "code": "ROUTE_NOT_FOUND",
    "message": "Route not found",
    "requestId": "6f1c…",
    "retryable": false
  }
}
```

- `code` is stable and machine-readable. Codes are `UPPER_SNAKE` and are
  added, never renamed or removed.
- `message` comes from a fixed catalogue. It never contains a library
  message, a stack trace, SQL or the rejected value.
- `requestId` is generated by the server and matches the request's logs. A
  client-supplied ID is logged beside it, never used in its place.
- `retryable` says whether repeating the same request can succeed.
- Validation errors add up to 10 `{ path, message }` issues, each capped at
  200 characters, never the values that were sent.

Each code belongs to one **kind**. The HTTP status and `retryable` come from
the kind, through tables that must cover every kind, so a new kind without
a status does not compile. Kinds are added in the phase that first needs
them; the first set is `invalid_input`, `not_found`, `payload_too_large` and
`internal`.

Only input parsed at the request boundary becomes `invalid_input`. A
validation failure on data Scryguard produced or stored (a database row, a
queue message, model output) is our fault and becomes `internal`. One error
handler maps everything else to `INTERNAL_ERROR`, logs the original with the
request ID and drops database error details from the log.

The contract covers the HTTP API. A review that fails inside the worker is
reported on the pull request as inconclusive (ADR 0007), not as an API
error.

## Consequences

- Callers decide on retries without parsing messages or guessing from
  status codes.
- Leaks are prevented by construction: response text comes from the
  catalogue, not from exceptions.
- The OpenAPI document publishes the shape. CI fails a pull request that
  breaks it, unless the pull request carries the `breaking-api-change`
  label.
- The catalogue grows with every phase and is maintained as part of the
  public contract.

## Alternatives considered

- **RFC 9457 Problem Details.** A recognised standard, but it has no retry
  signal, and its `detail` field invites passing exception text through.
- **OpenAI-style `type` and `param` fields.** Useful only for an
  OpenAI-compatible API, which Scryguard does not offer.
- **No `retryable` field.** Callers would infer it from the status code,
  which is ambiguous: a 503 may or may not be worth retrying.
- **Status and retry decided at each call site.** Flexible, but the two
  drift apart and are easy to get wrong.
